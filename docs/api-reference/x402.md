# x402

[x402](https://github.com/coinbase/x402) turns an HTTP `402 Payment Required`
into a paid resource. A merchant registers a slug and a price; a client requests
the slug, receives Stellar USDC payment requirements, pays on-chain, and retries
to unlock the content. SlipPay reuses the existing orders table, memo discipline,
listener and matcher — the x402 layer is a thin route over audited primitives.

Two mounts share the same router:

| mount | audience | auth |
|---|---|---|
| `/api/v1/x402-resources` | merchant registration and listing | API key |
| `/api/v1/x402` | payer-side gated GET | public |

## Register a resource

`POST /api/v1/x402-resources`

> **Auth**: API key (`Bearer sk_live_...`).

### Request

Exactly one of `inline_content` or `redirect_url` must be set.

```json
{
  "slug": "weather-rio",
  "usd_amount": "0.10",
  "inline_content": "{\"city\":\"Rio de Janeiro\",\"tempC\":28}",
  "inline_mime": "application/json",
  "description": "weather report, USDC gated"
}
```

| field | type | required | notes |
|---|---|---|---|
| `slug` | string | yes | 1–120 chars, `^[a-z0-9][a-z0-9-_]{0,119}$` |
| `usd_amount` | string | yes | decimal with 1–9 integer digits and up to 7 fractional digits; charged 1:1 as USDC |
| `inline_content` | string | one of | max 8192 chars; returned on payment |
| `inline_mime` | string | no | default `application/json`; max 120 chars |
| `redirect_url` | string | one of | valid URL; `302` target on payment |
| `description` | string | no | max 512 chars; echoed in the 402 body |

### Response

`201 Created`

```json
{
  "resource": {
    "id": "d4e5f6...",
    "slug": "weather-rio",
    "usd_amount": "0.10",
    "description": "weather report, USDC gated"
  },
  "url": "https://api.slippay.cc/api/v1/x402/weather-rio"
}
```

## List your resources

`GET /api/v1/x402-resources`

> **Auth**: API key.

```json
{
  "resources": [
    {
      "id": "d4e5f6...",
      "slug": "weather-rio",
      "usd_amount": "0.10",
      "description": "weather report, USDC gated",
      "created_at": "2026-10-19T18:24:00.000Z"
    }
  ]
}
```

Sorted by `created_at` descending. Only the authenticated merchant's resources
are returned.

## Fetch a gated resource

`GET /api/v1/x402/:slug`

> **Auth**: none. Rate-limited per client at 30 requests burst / 0.5 per second.

The response depends on the current state of the latest order for this
`(resource, client)` pair.

### First request — `402 Payment Required`

```json
{
  "x402Version": 1,
  "accepts": [
    {
      "scheme": "exact",
      "network": "stellar-testnet",
      "asset": "USDC:GBBD47IF...",
      "payTo": "GA5ZSEJY...",
      "maxAmountRequired": "0.10",
      "resource": "/api/v1/x402/weather-rio",
      "description": "weather report, USDC gated",
      "mimeType": "application/json",
      "payload": {
        "memo": "ce230c1913a3668164c8544ac49fd244fba452b19ddee02425386945a5e85cd2",
        "memoType": "hash",
        "recipient": "GA5ZSEJY...",
        "amount": "0.10",
        "assetCode": "USDC",
        "assetIssuer": "GBBD47IF...",
        "horizon": "https://horizon-testnet.stellar.org"
      }
    }
  ],
  "error": null
}
```

The same response carries:

| header | value |
|---|---|
| `x-payment-required` | `true` |
| `x-payment-memo` | the 32-byte hex memo to attach |
| `x-payment-network` | `testnet` or `mainnet` |

Pay `maxAmountRequired` of the named USDC asset to `payTo` with the issued memo
as a Stellar `Memo.hash`. The listener matches the payment and marks the order
`paid` through the same path as ordinary orders.

### Retry — pending

A retry while the order is still pending returns `402` again with the **same**
memo. Reuse it; do not create a second payment.

### Retry — paid

Once the listener has marked the order paid:

- `inline_content` resources return `200` with `inline_mime` (JSON is parsed and
  re-serialized; other MIME types are returned as-is);
- `redirect_url` resources return `302 Found` to the registered URL.

## Async status model

There is no x402-specific status endpoint. Status is the underlying order
status:

1. First GET creates a `pending` order with a fresh memo and a 30-minute expiry.
2. The client pays on-chain with that memo.
3. The Horizon listener matches memo + asset + recipient and marks the order
   `paid`.
4. The next GET from the same client identity sees `paid` and serves content.

The client identity is derived from the **trusted connection IP**, not a
client-supplied header. A payment made from one IP will not unlock the resource
for a retry from another IP. Keep the payer and the retry on the same egress.

## Abuse limits

| limit | value |
|---|---|
| per-IP request bucket on `/:slug` | 30 burst, refill 0.5/s |
| open pending orders per `(resource, client)` | 20 (`MAX_PENDING_PER_CLIENT_RESOURCE`) |
| open pending orders per resource | 500 (`X402_MAX_PENDING_PER_RESOURCE`) |

When a cap is hit the endpoint returns `429`:

```json
{ "error": "too_many_pending_orders", "scope": "client", "retry_after_sec": 60 }
```

## Errors

| status | code | when |
|---|---|---|
| 400 | `validation_error` | registration body failed validation; `issues` present |
| 400 | `operation_failed` | database write failed |
| 404 | `resource_not_found` | unknown slug |
| 409 | `constraint_violation` | slug already exists for this merchant (or another unique conflict) |
| 409 | `conflict_retry` | serialization failure; retry |
| 429 | `too_many_pending_orders` | open-order cap reached |
| 401 | `unauthenticated` | merchant route called without a valid API key |
| 503 | `merchant_not_configured` | the merchant has no Stellar receive address |

`STELLAR_NETWORK` must be set in production. The route fails closed rather than
advertising testnet asset details when `NODE_ENV=production` and the variable is
missing.
